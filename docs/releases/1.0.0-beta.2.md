# Groly 1.0.0-beta.2

A preview of Groly 1.0, with a comprehensively updated runtime and a verified direct upgrade path from 0.9.10. This release remains on the beta channel while the installed-iPhone PWA check is completed.

## Runtime and framework

- Node.js 24.22.0 LTS in development, builder and runtime; TypeScript 6.0.3 for supported tool compatibility.
- SvelteKit 3.1.0, Node adapter 6.0.0, Vite 8.3.4, Svelte plugin 7.3.1 and Vitest 5.0.4 migrated together. Native package imports replace the removed `$lib` alias; application state and navigation use the current framework APIs.
- Paraglide 2.28.0 with a version-pinned message-format plugin and request-local server language state. German/English translations and stored language preferences remain compatible.
- SQLite driver 13.0.3 runs in the actual amd64 Alpine image. No application schema or IndexedDB version change; existing password hashes, sessions and API payloads are preserved.
- Runtime `ORIGIN`, proxy settings, volume path, port and VAPID configuration remain supported. The start wrapper preserves origin validation and the framework's CSRF protection.
- Service-worker precache generation runs before adapter asset hashing/compression. The build verifies injected references and matching gzip/Brotli output. Existing PWA storage and queued mutations remain in place.
- PDF export uses the same pdfmake 0.3.11 browser runtime, loaded as its hashed prebundled asset, and all four original Roboto faces as binary TTF assets. The runtime and fonts remain available in the offline precache. Report data loading requires a server connection; failures show a bilingual message and preserve selected options for retry.

## Dates: issue #17

Meal planning now stores local calendar dates instead of converting local midnight to UTC. Supplement date bounds, caffeine quick logging and PDF filename dates use the existing local-date helpers too.

Existing meal-plan values are deliberately not shifted: their original timezone cannot be recovered reliably. Affected old entries may appear one day earlier; move them to the intended day. No automatic bulk date migration runs.

## Backups and release safety

- Before initializing a new version against an existing database, create a SQLite backup (including committed WAL data), copy uploads, verify checksums and database integrity, flush files/directories and atomically publish the snapshot. Migration, bootstrap, cleanup and normal requests wait for completion.
- Insufficient space, unwritable directories or damaged snapshots block startup. Completed backups and interrupted partial folders are retained. Same-version restarts skip duplicate copies; interrupted initialization reuses its verified snapshot. A restored old database gets a new snapshot on a subsequent upgrade.
- Unauthenticated `/api/health` returns 200 only after successful initialization, otherwise 503. Docker allows ten minutes for backup/startup, configurable for larger installations.
- Docker build context excludes local data, credentials and generated files. The runtime uses pinned Alpine 3.24.2 plus the exact Node 24.22.0 binary and its license from the pinned official Node image. It omits development tools, npm/Yarn/Corepack, SDK headers, browser packages, foreign SQLite binaries, SQLite compilation sources and Drizzle generation snapshots. All migration SQL files and the migration journal remain present. Browser-only PDF code/fonts are excluded from the server build. The unused ZXing dependency is removed; the existing native/ZBar barcode implementation remains.
- Release workflow uploads an untagged candidate by digest, pulls its immutable registry reference, scans it and runs the upgrade/browser gates. After verification, only the exact version tag and its matching channel are assigned, with a digest equality check for each. Manual runs build and verify a local runner image without registry login or image pushes. There are no extra candidate tags. Architecture remains amd64; beta and latest remain separate.
- See [English and German upgrade/restore instructions](../UPGRADING.md). Keep an independent backup of the complete data volume; local snapshots do not cover disk loss.

## Verification baseline

The application code is unchanged from the fully verified warning-cleanup commit `1e4f2a384b61d0b9a83a9635bd9569634f023d31`; beta.2 updates version/changelog metadata. The [single Ubuntu 26.04 verification run](https://github.com/peterthepeter/groly/actions/runs/38746578949) passed without retry or warning diagnostics. These baseline results are repeated against the actual beta.2 registry image during release verification.

- Clean `npm ci --ignore-scripts`, prepare, type check (zero errors/warnings), 300 application tests, 13 release-policy tests, dependency/migration-generator checks and production build pass on Node 24.
- Original images 0.9.10, 0.9.9 and 0.9.8-hotfix.2 upgrade directly using fresh copies of the original fixtures each time. All 45 table inventories, schemas and row digests, identifiers, relationships, settings, password hashes, existing sessions and image checksums are compared. Documented automatic housekeeping metadata is excluded.
- A separate local copy of an existing installation, including eight uploaded images, passes the same upgrade/restart/restore checks. The original directory is untouched; isolated test containers cannot send external notifications.
- Fresh admin bootstrap/login, image upload/serving, authenticated pages/APIs, SSE connection, CSV export, queued tracker idempotency and CSRF rejection are exercised in the production container.
- Restart creates no duplicate snapshot. Disk-full and permission failures return 503 on repeated requests without changing user data. Tests cover interrupted partial backups, damaged/missing snapshots, WAL contents and rollback followed by new old-version writes.
- Each automatic snapshot is restored to a separate volume and started successfully with its matching original image.
- Chromium and desktop WebKit exercise an existing 0.9.10 service worker, session and offline mutation queue through the upgrade, verify exactly one synchronized item, core pages, local-date meal planning, an actual PDF download, cold offline PDF runtime/font loading, failed-export handling, retry after reconnecting and persistent language switching.
- Date tests cover UTC, Berlin, Moscow, New York and Kiritimati, including local midnight, DST, leap day and month/year boundaries.

## Security and remaining checks

- Full development and production dependency audit: zero reported vulnerabilities. The verified application baseline's final image scan reports zero findings across all severities, including the Alpine zlib fix (1.3.2-r1). The beta.2 registry image is scanned again before channel promotion.
- Stable Drizzle Kit 0.31.11 uses a reproducible metadata-only package patch removing its unused, abandoned esm-loader dependency before installation. All executable files remain unchanged. The upstream archive is SHA-512 verified, the patched archive reproduces byte-for-byte, and migration-generator fixtures validate no-op and new-table behavior. See [patch details](../../vendor/README.md).
- Workbox's glob dependency is resolved explicitly to stable 13.0.6. Its actual precache generation and PWA-upgrade behavior are exercised by the build/browser gates. No forced peer dependencies or audit suppressions are used.
- PWA's integration hook replaces the deprecated inlineDynamicImports option with codeSplitting=false. Application chunks, PDF vendor asset size, all font signatures and their precache membership are checked. Build warnings fail the build instead of being suppressed.
- GitHub CI explicitly runs on Ubuntu 26.04 with current actions/cache 6.1.0. Browser engines are cached; Docker cache export uses a dedicated amd64 scope and mode=min. All release gates remain enabled.
- Actual installed-iPhone PWA testing is pending before stable: login, language switching, offline creation/reconnect, push, supplements and meal planning. Desktop WebKit does not substitute for this check. Physical camera/barcode access and live third-party push delivery need device/environment validation.
- These tests establish the supported upgrade paths against tested data; they cannot guarantee every operator-specific storage/proxy setup. Existing mount and environment settings must be retained. Large upload collections may require more startup time and disk space.
